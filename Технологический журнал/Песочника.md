


Это просто отличная задача для применения тех самых скриптов `gawk`, которые были в твоей шпаргалке! 

Поскольку ты хочешь найти **«Кто больше всего захватил СУБД»**, нам нужно искать события **`DBPOSTGRS`**, которые выполнялись внутри открытой транзакции (**`Trans=1`**). Именно они являются виновниками того, что в консоли 1С растет счетчик «Захвачено СУБД».

Вот готовый, мощный скрипт для твоего терминала Linux, который сделает всю грязную работу, переведет микросекунды в нормальные секунды и выведет **Топ-15 главных вредителей** за ночь.

---

### Твой готовый скрипт (скопируй и вставь в консоль)

*(Предполагается, что твои логи лежат в `/var/log/1c/heavy_sql/` или похожей папке. Замени путь на свой, если нужно).*

```bash
cat /var/log/1c/heavy_sql/rphost_*/*0[1-7].log | \
gawk -v RS='[0-9]{2}:[0-9]{2}\\.[0-9]{6}-' \
'/DBPOSTGRS/ && /Trans=1/ {
    
    # 1. Извлекаем длительность (до первой запятой) и переводим в секунды
    split($0, a, ",");
    dur_sec = a[1] / 1000000;

    # 2. Ищем пользователя (Usr=...)
    if (match($0, /Usr=([^,]+)/, u)) {
        user = u[1];
    } else {
        user = "Фоновое/Система";
    }

    # 3. Ищем контекст (первую строчку кода, чтобы понять, что он делал)
    if (match($0, /Context=([^\n]+)/, c)) {
        ctx = c[1];
    } else {
        ctx = "Нет контекста";
    }

    # 4. Выводим красиво отформатированную строку
    printf "%9.2f сек | %-20s | %s\n", dur_sec, user, ctx;
    
}' | sort -nr | head -n 15
```

---

### Как работает эта магия (Разбор по косточкам):

1. **`cat .../rphost_*/*0[1-7].log` (Фильтр по времени)**
   В 1С само время пишется внутри файла, но **часы** пишутся в названии файла (например, `26041001.log` — это лог за 01:00 ночи). 
   Конструкция `*0[1-7].log` заставит Linux прочитать файлы только с `01` до `07` (то есть логи с 01:00:00 до 07:59:59 утра).

2. **`-v RS='[0-9]{2}:[0-9]{2}\.[0-9]{6}-'` (Борьба с переносами)**
   Это тот самый трюк из твоей шпаргалки! Так как текст SQL-запроса многострочный, мы говорим `gawk`: *"Считай концом события не нажатие Enter, а момент, когда увидишь дату и дефис следующего события (например `12:34.567890-`)"*.

3. **`'/DBPOSTGRS/ && /Trans=1/'` (Главный фильтр)**
   Мы берем только запросы к базе данных, которые шли **внутри транзакции**. Именно они блокируют таблицы.

4. **`match($0, /Usr=([^,]+)/, u)` (Регулярка внутри gawk)**
   Это функция GNU Awk, которая ищет слово `Usr=`, берет всё, что написано после него до первой запятой, и кладет в переменную `u[1]`. То же самое мы делаем для `Context`, но там мы берем текст до первого переноса строки (`\n`), чтобы не выводить портянку кода на весь экран.

5. **`sort -nr | head -n 15` (Рейтинг)**
   Сортируем как числа (`-n`) в обратном порядке (`-r` — от большего к меньшему) и выводим Топ-15 (`head`).

Проблема с неработающей отладкой на Linux-сервере — это классика, через которую проходит каждый системный администратор 1С. Разработчики всегда будут говорить: *"Я ставлю точку останова, а она не срабатывает, ваш сервер меня не видит!"*.

Помнишь твой скриншот, где мы поймали ошибку **`Connection reset by peer`** от пользователя с приложением **`Debugger`**? Это как раз оно!

Давай разберем по шагам, как с помощью Технологического журнала (ТЖ) и системной логики найти, где рвется связь между Конфигуратором разработчика и твоим сервером.

---

### ШАГ 1. Базовая проверка Админа (Без ТЖ)

Прежде чем лезть в логи, проверь самое главное правило: **Включен ли вообще режим отладки на сервере?**
Если у службы `ragent` нет ключа `-debug`, сервер 1С вообще не будет слушать команды отладчика.

1. Открой настройки службы твоего тестового кластера (где они кодят):
   `sudo systemctl edit srv1cv8-8.3.24.1500@dev.service` (твой инстанс).
2. Убедись, что в параметрах запуска (если они переопределены) или в основном файле службы есть ключ **`-debug`**.
   *Если его нет — добавь, сделай `daemon-reload` и перезапусти службу. Возможно, логи ТЖ тебе даже не понадобятся!*

---

### ШАГ 2. Настраиваем "Ловушку для Отладчика" в `logcfg.xml`

Если `-debug` включен, а отладка не цепляется, мы должны отследить сетевой путь программиста.

Мы будем ловить события **`CONN`** (подключения) и **`EXCP`** (ошибки), но чтобы не забить диск, поставим жесткий фильтр: **ловить только Отладчик**.

Добавь этот блок в свой `logcfg.xml`:

```xml
<log location="/var/log/1c/debug_test" history="24">
    <!-- Ловим сетевые подключения отладчика -->
    <event>
        <eq property="Name" value="CONN"/>
        <eq property="t:applicationName" value="Debugger"/>
    </event>
    <!-- Ловим сетевые ошибки отладчика -->
    <event>
        <eq property="Name" value="EXCP"/>
        <eq property="t:applicationName" value="Debugger"/>
    </event>
    <property name="all"/>
</log>
```
*Сохрани файл и попроси программиста запустить отладку.*

---

### ШАГ 3. Анализируем логи (Где рвется связь?)

Открываем папку `/var/log/1c/debug_test/` и смотрим, что там появилось. Возможны 3 сценария.

#### Сценарий А: В логах вообще ПУСТО
*   **Диагноз:** Запрос от компьютера программиста даже не дошел до службы 1С на Linux.
*   **Решение:** Проверяй **Фаервол (UFW / Firewalld)** на Linux-сервере или корпоративный антивирус. Порты отладки (обычно 1560-1591) жестко заблокированы снаружи.

#### Сценарий Б: Есть `EXCP` с текстом `Connection refused` или `Timeout`
*   **Диагноз:** Конфигуратор программиста дошел до менеджера кластера, получил команду *"Иди отлаживаться на порт 1564"*, пошел туда, а там его не пустили.
*   **Решение:** Это частая беда на Linux. Для отладки клиентский ПК (Windows) и сервер (Linux) должны иметь **двустороннюю открытую связь** по всем динамическим портам кластера. Убедись, что программист стучится на правильный IP, и что на сервере открыт ВЕСЬ диапазон портов (например, `1660:1691/tcp` для твоего второго кластера).

#### Сценарий В: Есть `CONN` со статусом `disconnected` и `Calls=0`
*   **Диагноз:** Программист сам (или его антивирус) рвет соединение. Это тот самый лог, который мы видели у тебя ранее: `Connection reset by peer`.
*   **Решение:** Искать проблему на компьютере самого программиста (Брандмауэр Windows часто блокирует входящие соединения для `1cv8.exe`, а для отладки они нужны).

### 🚀 ЛАЙФХАК АДМИНА: Перевод на HTTP-отладку (Решает 99% проблем)

Исторически 1С использует **TCP-отладку**. Это значит, что сервер 1С и Конфигуратор пытаются хаотично открывать порты друг к другу. В сложных сетях с NAT, Docker или строгими фаерволами это **всегда не работает**.

Фирма 1С придумала современный метод: **Отладка по протоколу HTTP**.
Она работает через один конкретный порт, и фаерволы ее не режут.

**Как перевести разработчиков на HTTP-отладку:**
1. В параметрах запуска службы 1С (в Linux) замени старый ключ `-debug` на новый:
   **`-debug -http`**
2. Перезапусти службу 1С.
3. Скажи программистам: *"В Конфигураторе зайдите в Сервис ➔ Параметры ➔ Отладка. Выберите «Отладка по протоколу HTTP»"*.
4. **БИНГО!** Отладка начнет работать как часы, потому что весь трафик пойдет по стандартным и понятным HTTP-туннелям.
