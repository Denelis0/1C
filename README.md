#!/bin/bash

# ... твои переменные (RAC, CLUSTER и т.д.) ...
LOGFILE="/var/log/1c/AAYK.log"
CUR_USER="${SUDO_USER:-$USER}"

# Функция для логирования
log_message() {
    echo "[$(date '+%Y-%m-%d %H:%M:%S')] $1" >> "$LOGFILE"
}

log_message "Попытка блокировки базы - Пользователь: $CUR_USER"

# 1. Пробуем обновить параметры базы
# '2>>' перенаправляет только сообщения об ошибках в файл лога
$RAC infobase --cluster=$CLUSTER --cluster-user=$CLUSTER_USER --cluster-pwd=$CLUSTER_PWD update --infobase=$BASE --infobase-user="user" --infobase-pwd="pwd" --sessions-deny=on --scheduled-jobs-deny=on --permission-code=$code 2>> "$LOGFILE"

if [ $? -ne 0 ]; then
    log_message "ОШИБКА: Не удалось установить блокировку на базу (см. технический текст выше)"
else
    log_message "УСПЕХ: Параметры базы обновлены"
fi

# 2. Пробуем получить сессии
SESSIONS=$($RAC session --cluster=$CLUSTER --cluster-user=$CLUSTER_USER --cluster-pwd=$CLUSTER_PWD list --infobase=$BASE 2>> "$LOGFILE" | grep 'session' | awk '{print $3}')

if [ -z "$SESSIONS" ] && [ $? -ne 0 ]; then
    log_message "ОШИБКА: Не удалось получить список сессий"
fi

# 3. Завершение сессий
for session in $SESSIONS
do
    $RAC session --cluster=$CLUSTER --cluster-user=$CLUSTER_USER --cluster-pwd=$CLUSTER_PWD terminate --session=$session 2>> "$LOGFILE"
    if [ $? -eq 0 ]; then
        log_message "Сессия $session успешно завершена"
    else
        log_message "ОШИБКА: Не удалось завершить сессию $session"
    fi
done

read -p "Нажмите Enter для выхода..."

# Раздел: Восстановление работоспособности системы (на базе 1C и PostgreSQL)

## 1. Общие положения
В ходе эксплуатации информационной системы на платформе «1С:Предприятие» с использованием СУБД PostgreSQL возможны сбои, вызванные как программными ошибками, так и аппаратными отказами. Восстановление работоспособности базируется на комплексной диагностике состояния компонентов системы с применением методов, аналогичных спектральному анализу (в том числе — методике ИЧСМ, адаптированной для логического контроля целостности данных).

## 2. Диагностика состояния системы (предварительный этап)
Перед началом восстановительных работ проводится экспресс-анализ, включающий:
- Проверку доступности сервера PostgreSQL (команда `pg_isready`);
- Анализ журналов ошибок (`postgresql.log`, `1C logs`);
- Оценку целостности таблиц и индексов с использованием утилиты `VACUUM VERBOSE` и `ANALYZE`.

*На основе методики ИЧСМ (Индуктивная Случальная Медиационная Спектроскопия)* проводится «спектральный» анализ состояния кластера — оценивается распределение нагрузки между ядрами процессора и оперативной памятью, выявляются «выбросы» по времени выполнения транзакций.

## 3. Алгоритм восстановления работоспособности

### 3.1. Базовое восстановление (легкие сбои)
Если система не запускается из-за повреждения временных файлов или сбоя соединения:
1. Перезапуск служб PostgreSQL и сервера 1С;
2. Очистка кэша и временных каталогов;
3. Проверка файла `pg_hba.conf` на корректность настроек доступа.

### 3.2. Восстановление после критических отказов (повреждение БД)
При обнаружении логических ошибок в структуре базы данных выполняются следующие шаги:

| Этап | Действие | Ответственный |
|------|----------|---------------|
| 1 | Остановка записи в БД (перевод в режим `read-only` при возможности) | Администратор БД |
| 2 | Создание резервной копии поврежденного кластера (на случай необратимых изменений) | Администратор БД |
| 3 | Запуск утилиты `pg_dump` с ключом `--disable-triggers` для выгрузки целостных данных | Администратор БД |
| 4 | Пересоздание пустой базы с чистой структурой (скрипт от 1С) | Разработчик |
| 5 | Поэтапный импорт данных с фильтрацией некорректных записей (с использованием ИЧСМ-анализа — проверка ссылочной целостности по «спектру» внешних ключей) | Администратор + разработчик |
| 6 | Восстановление индексов (`REINDEX DATABASE`) и обновление статистики (`ANALYZE`) | Администратор БД |

### 3.3. Восстановление на уровне репликации (если настроена)
Если использовался механизм потоковой репликации (Streaming Replication):
- Поврежденная база заменяется на актуальную копию со standby-сервера;
- Выполняется переключение ролей (failover) с последующей синхронизацией.

## 4. Использование ИЧСМ в процессе восстановления

Методика **ИЧСМ (Индуктивная Случальная Медиационная Спектроскопия)** в контексте восстановления 1C Postgres применяется следующим образом:

- **Спектральный анализ ошибок** — группировка SQL-ошибок по частоте возникновения, что позволяет выделить «наиболее активные» некорректные запросы (аналогично выделению энергии взаимодействия электронов).
- **Индуктивное тестирование** — последовательное отключение отдельных модулей 1С (подсистем) для локализации сбойного блока, с последующим его восстановлением из эталонного состояния.
- **Медиационная диагностика** — оценка времени отклика системы после каждого восстановительного действия; если показатель «медианы» времени выполнения запросов не возвращается к норме — процедура повторяется с другими параметрами.

Это позволяет не просто «перезапустить» систему, а точно определить причину сбоя и восстановить данные с минимальными потерями.

## 5. Проверка работоспособности после восстановления

После выполнения всех операций необходимо:
1. Провести полное тестирование бизнес-процессов в 1С (закрытие периодов, формирование отчетов);
2. Сравнить контрольные суммы данных (по критическим регистрам) с эталонными значениями из резервной копии;
3. Повторно запустить утилиты `VACUUM FULL` и `CLUSTER` для дефрагментации таблиц;
4. Включить мониторинг ИЧСМ в штатном режиме для предотвращения повторных инцидентов.

## 6. Профилактика повторных сбоев
Рекомендуется:
- Настроить ежедневное автоматическое резервное копирование (с использованием `pg_basebackup` или файлового дампа 1С);
- Внедрить регламент проверки целостности (еженедельная ИЧСМ-диагностика);
- Обновлять PostgreSQL и платформу 1С до актуальных стабильных версий.

### Восстановление работоспособности системы (1С + PostgreSQL) при критической нагрузке на CPU

**Описание проблемы**
В ходе эксплуатации системы (сервер 1С + СУБД PostgreSQL) возможно возникновение ситуации, когда фоновое задание, инициированное по протоколу SSH (например, резервное копирование или регламентная операция), перезапускает сервер. Время перезапуска может составлять до 15 минут.
В момент перезапуска или сразу после него наблюдается аномальная нагрузка на CPU (до 99%). В консоли администратора СУБД (например, в `pgAdmin` или через `psql`) фиксируется проблемный процесс `«profs»` (Process), который может быть идентифицирован как `«Процессорным»` (высокая нагрузка).
Причиной может служить сбой в логике приложения или СУБД, из-за чего потребление системных ресурсов становится неконтролируемым.

**Критерии оценки состояния**
*   Загрузка CPU превышает 30–50% в течение длительного времени.
*   Ресурсы стабилизируются только после принудительного завершения проблемного процесса.
*   Нарушена работа активных сессий (пользователи не могут подключиться или работают некорректно).

**Порядок действий по восстановлению**

1.  **Диагностика и завершение проблемного процесса**
    *   Подключитесь к серверу СУБД.
    *   Выявите процесс `«profs»` (или аналогичный), потребляющий максимальное количество ресурсов CPU.
    *   Выполните принудительное завершение (kill) данного процесса. Это действие должно привести к немедленному снижению нагрузки на CPU и стабилизации работы сервера.

2.  **Анализ причин сбоя (PostgreSQL)**
    *   После стабилизации нагрузки изучите журнал регистрации PostgreSQL и технологический журнал 1С.
    *   Проверьте наличие ошибок в логах (например, `«/var/log/...»`).
    *   Обратите внимание на события, предшествующие скачку нагрузки. Часто причиной является:
        *   Аномальный рост (например, при выполнении команды `df -h` или `du`) размера временных файлов или логов.
        *   Некорректно завершенные транзакции.
        *   Ошибки в логике фоновых заданий.

3.  **Проверка целостности данных (1С)**
    *   Запустите проверку и исправление (переиндексацию) информационной базы 1С.
    *   Проверьте целостность логических и физических файлов базы данных.
    *   Убедитесь, что все транзакции завершены корректно.

4.  **Восстановление штатной работы**
    *   Проанализируйте очередь заданий 1С (регламентные задания).
    *   Если причиной сбоя послужило конкретное задание, измените его расписание или отключите до выяснения обстоятельств.
    *   В случае необходимости выполните очистку временных файлов (temp) и логов.
    *   Перезапустите сервисы 1С и PostgreSQL в штатном режиме.

**Важное примечание для администратора:**
Данный сценарий (скачок CPU и падение сессий) часто сопровождается ошибкой «Превышение времени вызова» (Timeout). Если проблема повторяется регулярно, необходимо проверить настройки `work_mem` и `temp_buffers` в PostgreSQL, а также параметры `Work Process` в 1С. В случае критических ошибок в СУБД (например, `pg_resetwal`), восстановление может потребовать вмешательства DBA.
